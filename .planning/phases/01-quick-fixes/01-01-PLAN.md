<objective>
Give Windows SSE the same resilience macOS already has: when the event stream drops because of a transient network hiccup, the client reconnects with exponential backoff instead of marking the recording as failed. Closes the gap where a momentary connection loss surfaces an "onterechte failed" status to the user.

Purpose: Cross-platform parity (C-01) — macOS `SSEClient` in `macos/Services/APIService.swift` reconnects up to 5 times with `pow(2, attempt)` backoff capped at 16s. Windows currently has no reconnect at all.
Output: A reconnecting `SSEClient` (TS) backed by a Rust stream command that distinguishes a clean `[DONE]` from an interrupted stream.
</objective>

Listen for the new `{eventName}-interrupted` event in addition to `{eventName}-done`. On `-interrupted`: if `terminalReached` is true, treat as completion (disconnect + onComplete); otherwise call a new private `reconnect()`. `reconnect()`: if `reconnectAttempts >= maxReconnectAttempts` → disconnect + onError(new Error("SSE verbinding verbroken")); else `reconnectAttempts += 1`, compute `backoffMs = Math.min(2 ** reconnectAttempts, 16) * 1000` (yields 2s,4s,8s,16s,16s — identical curve to macOS), `setTimeout` that delay, then re-run the connect/invoke sequence with the SAME url, token and a FRESH `eventName` (re-listen, re-invoke `http_sse_stream`). The existing `-done` handler stays as clean completion (reset attempts, onComplete). The catch around `invoke("http_sse_stream", ...)` should also route through `reconnect()` instead of immediately calling onError, so a connect-time failure retries too. Reset `reconnectAttempts = 0` only on a successful reconnect that yields further data or on clean done. Ensure `disconnect()` clears any pending reconnect `setTimeout` and unlistens the `-interrupted` listener so a stopped client never reconnects (parity with macOS `isStopped`).
